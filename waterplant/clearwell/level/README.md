# 清水池液位闭环（clearwell.level）

## 解决的问题

旧逻辑只按一个目标液位先后挪动进水、出水阀门，既不看进出水流量差，也不知道泵组
能承担多少；泵组一启一停，液位就大幅波动。本子包把它换成一个有质量平衡、有泵组
时序、有保护联锁和有审计的闭环。

## 固定下来的两条策略（不再随班次/工况漂移）

1. **上下限按有效池容算，不按班次用量算。**
   LL/L/H/HH 分别是死液位到最高液位之间有效量程的 5%/15%/85%/95%，
   见 `config.py`。班次用量只能调目标液位（`POST /clearwell/level-loop/target`），
   目标必须严格落在联锁限之内；没有任何接口能改联锁比例或池容。

2. **波动大时压调节速度，绝不放宽上下限。**
   每拍允许的净流量变化来自池容（有效池容 / 标称放空小时数）；波动拍把预算减半，
   阀门还有每拍行程限速。只有越过 HH/LL 的硬保护允许朝安全方向更快动作。

## 一个节拍的四阶段时序

`LevelLoop.tick` 严格按顺序执行，且每阶段都进审计：

```
read_inputs -> confirm_pumps -> decide_valves -> dispatch
```

* **先确认泵组再算阀门。** `confirm_pumps` 推进 STARTING/STOPPING 计时器，是每个
  节拍唯一的一次确认（重复确认会让泵时序跑快，已用测试钉死）。
* 泵组处于过渡态时，液位 PI 冻结，出水阀朝需求、进水阀同步跟随（净流目标为 0），
  即一次前馈预偏置；同一过渡的前馈只宣布一次，重复节拍收敛到同一阀位。
* 启/停泵由“需求 vs 在运泵容量”驱动，并有两拍防抖：
  需求持续超过在运泵出力（或阀已开满仍供不上）才启泵；
  需求持续降到少一台泵也能承担（带迟滞）才停泵。

## 进出水分工与调节量

* **进水阀是主执行器**：负责质量平衡与液位 PI 校正，受池容 slew 预算限速。
* **出水阀只做微调/跟随**：在泵组能承担的 `[min, max]` 包络内朝需求开，
  超不出泵的能力；供不上的部分作为残差交给泵序，而不是硬掰阀门。
* 调节量 = 目标净流（液位 PI 项），在进水/出水间按上述分工分配，
  再与泵包络、保护带、slew 预算取交集。

## 保护

* H 区按剩余水头比例挤压进水，L 区按剩余水深比例挤压出水；
* ≥HH：进水快关、出水快开，并强制下一台可用泵；
* ≤LL：进水快开、出水快关，并停掉一台在运泵；
* 自相矛盾（同时 HH 与 LL，不可能是真实液位）：safe hold。

## 液位计读不到：部分失败

* 液位计失效不是整站失败。流量计、泵组继续工作；
  液位改用净流积分估计，不确定度逐拍增长，增益减半、出水只小幅跟随、禁止自动启泵；
* 不确定度超过上限进入 safe hold，等操作员；
* 恢复时直接采用实测液位（无冲击 bumpless），不追补陈旧误差；
  恢复后重复触发是幂等的——相同阀位不再发第二次指令，相同泵启停不再下第二次命令。

## 一致性、审计与展示

每个节拍产出**同一个** `Decision` 对象：动作（action）、所依据液位（level_m /
level_used_m）、原因（reason 代码）、阀门/泵指令、相位日志、抑制项与备注。
它既被派发现场，又原样写入哈希链审计，并原样供控制台展示，三者不可能不一致。

* `GET  /clearwell/level-loop`              状态、固定保护带、阀位、泵组、策略
* `GET  /clearwell/level-loop/band`         按池容算出的联锁带（米与立方）
* `POST /clearwell/level-loop/target`       班次只能改目标，不能改联锁
* `POST /clearwell/level-loop/tick`         送一组读数，跑一个闭环节拍
* `GET  /clearwell/level-loop/audit`        哈希链审计
* `GET  /clearwell/level-loop/audit/verify` 校验审计链完整性
* `POST /clearwell/level-loop/demo`         确定性脚本场景（扰动/启泵/失效/恢复）

状态同时进入 `/snapshot`、`/report` 与 `/health/checks`
（`level_loop` 正常/降级/安全保持，`level_audit` 哈希链是否完好）。
